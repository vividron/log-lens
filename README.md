## Overview

LogLens is a small observability-style platform for analyzing application/server logs.

It allows a user to:

1. Upload CSV or JSON logs.
2. Validate and normalize records.
3. Store logs in MongoDB.
4. Detect unusual behavior using an explainable anomaly-scoring algorithm.
5. Search, filter, paginate, and inspect logs.
6. Investigate detected anomalies.
7. Ask Gemini to explain an already-detected anomaly.
8. View a likely cause and recommended next step.

The central design principle is:

```text
Your Detection Engine → finds the anomaly
Gemini AI             → explains the anomaly
```

AI is not used as the source of truth for anomaly detection.

---

## Problem Statement

Application logs can contain thousands of normal events mixed with a small number of important failures or unusual behaviors.

A developer needs to quickly answer:

- Which events are unusual?
- How severe are they?
- Why were they flagged?
- What might have caused them?
- What should be investigated next?

LogLens addresses these questions with deterministic detection plus AI-assisted investigation.

---

## Solution

The application uses two stages.

### Stage 1 — Detection

The backend evaluates:

- HTTP severity
- Repeated failures
- Request-rate deviation
- Source behavior changes

These signals contribute to an anomaly score from `0–100`.

### Stage 2 — Investigation

When a user opens an anomaly, Gemini receives the original log plus the evidence generated by the detector and returns:

- What happened
- Likely cause
- Recommended next step

This keeps the detection layer deterministic and the AI layer explanatory.

## Log Data Model

Incoming records are normalized into a common schema:

```json
{
  "timestamp": "2026-08-20T09:15:10Z",
  "source": "10.0.0.55",
  "eventType": "http_request",
  "severity": "error",
  "status": 500,
  "endpoint": "/api/payment",
  "message": "POST /api/payment - internal server error"
}
```

After detection:

```json
{
  "isAnomaly": true,
  "anomalyScore": 86,
  "anomalyLevel": "critical",
  "detectionReasons": [
    {
      "type": "severity",
      "message": "HTTP 500 server error",
      "points": 40
    },
    {
      "type": "frequency",
      "message": "Multiple failures from this source",
      "points": 25
    },
    {
      "type": "rate",
      "message": "Request rate is significantly above baseline",
      "points": 21
    }
  ]
}
```

AI analysis is stored separately:

```json
{
  "aiAnalysis": {
    "explanation": "...",
    "likelyCause": "...",
    "recommendedNextStep": "...",
    "generatedAt": "..."
  }
}
```

## Anomaly Detection Approach

### Hybrid Explainable Scoring

The detector combines deterministic rules with statistical behavior:

```text
Anomaly Score =
    Severity Score
  + Frequency Score
  + Rate Deviation Score
  + Behavior Deviation Score
```

The score is classified as:

| Score | Level |
|---:|---|
| 0–29 | Normal |
| 30–59 | Suspicious |
| 60–79 | High |
| 80–100 | Critical |

### 1. Severity

Example signals:

```text
2xx       → 0
3xx       → 0
404       → +10
401       → +15
403       → +25
429       → +25
5xx       → +40
```

A 500 error is not automatically an anomaly; it is one signal.

### 2. Repeated failures

The detector looks for multiple failures from the same source within a short time window.

```text
10:15:01  10.0.0.55  500
10:15:05  10.0.0.55  500
10:15:09  10.0.0.55  500
10:15:13  10.0.0.55  500
```

### 3. Request-rate deviation

A baseline is calculated from the uploaded dataset.

If a source normally generates 5–8 requests/minute and suddenly generates 100 requests/minute, the deviation increases the score.

Historical timestamps are compared with other timestamps in the dataset rather than with the current system time.

### 4. Source behavior

A source that normally produces successful requests but suddenly generates many 403/500 responses receives additional anomaly points.

---

## Why This Algorithm?

A pure ML model such as Isolation Forest would be possible, but the hybrid approach was chosen intentionally.

### Explainability

Instead of:

```text
ML anomaly score = 0.82
```

the application can show:

```text
HTTP 500 error             +40
Repeated failures          +25
High request rate          +21
------------------------------
Total                       86
```

This makes the result easy for a developer to understand.

### No training dataset required

The system can work directly with an uploaded dataset.

### Easy to validate

The generated assessment dataset contains known anomaly patterns, making the detector easy to test.

### AI independence

The core detection system remains functional even if Gemini is unavailable.

## AI Architecture

AI is deliberately separated from anomaly detection.

```text
Log
 ↓
Anomaly Detector
 ↓
Score + Evidence
 ↓
isAnomaly = true
 ↓
User requests analysis
 ↓
Gemini
 ↓
Explanation + Cause + Next Step
```

The Gemini prompt explicitly tells the model that the anomaly has already been detected.

This prevents the LLM from becoming the source of truth for detection.

### Why AI is on-demand

Suppose 1,000 logs produce 50 anomalies.

Calling Gemini 50 times during upload would:

- slow ingestion
- increase API usage
- generate explanations the user may never read

Instead:

```text
Upload
 ↓
Detect anomalies
 ↓
Persist
 ↓
User opens anomaly
 ↓
One Gemini request
```

AI results can then be cached in MongoDB.

## Performance Considerations

### Pagination

Logs are paginated at the database level rather than loading the entire collection into React.

### On-demand AI

Gemini is only called when an anomaly is investigated.

### Persistence

Anomaly scores are calculated during ingestion and stored, avoiding repeated calculations on dashboard requests.

### Indexing

Frequently queried fields such as:

- timestamp
- source
- severity
- isAnomaly
- anomalyScore

can be indexed.

## Engineering Decisions

### REST instead of WebSockets

The assessment focuses on uploaded datasets and investigation rather than live streaming. REST keeps the implementation simple and maintainable.

### Detect during ingestion

Detection is deterministic and relatively inexpensive, so it is calculated once and persisted.

### AI on demand

AI calls are more expensive than deterministic scoring and are only useful when a user investigates an anomaly.

### Store detection reasons

Every anomaly stores the evidence behind its score. This improves explainability and provides structured context to the AI layer.

### AI does not detect anomalies

The LLM is probabilistic. The core monitoring signal should be deterministic and reproducible.

---

## Limitations

This implementation is intentionally scoped for a technical assessment.

- Scoring weights are manually designed.
- Baselines are dataset-based.
- There is no real-time log streaming.
- Authentication/workspaces are outside the current scope.
- Large-scale distributed processing is not implemented.
- The detector would require tuning against labeled production incidents before production deployment.

## Interview / Design Summary

The entire system can be summarized as:

```text
                 LOG FILE
                    │
                    ▼
             Parse + Validate
                    │
                    ▼
                Normalize
                    │
                    ▼
          ┌─────────────────────┐
          │  Anomaly Detection  │
          │                     │
          │  Severity           │
          │  Frequency          │
          │  Rate Deviation     │
          │  Behavior Change    │
          └──────────┬──────────┘
                     │
                     ▼
              Score 0–100
                     │
                     ▼
                 MongoDB
                     │
                     ▼
             User investigates
                     │
                     ▼
                 Gemini AI
                     │
            ┌────────┼────────┐
            ▼        ▼        ▼
       Explanation  Cause  Next Step
```

The key architectural principle is:

> **Detection is deterministic; AI is explanatory.**

This keeps the system simple enough for the assessment while making the results explainable, testable, and extensible.
